# CONCERTO — BUSINESS PLAN: Venue / Promoter Partnerships (Ξεχωριστό Brief)

## Σκοπός αυτού του εγγράφου

Αυτό είναι **ξεχωριστό, επιχειρηματικό** brief — όχι τεχνικό. Αφορά την επέκταση του Concerto ώστε να καλύψει όχι μόνο artists/bands, αλλά και **venues/live stages/promoters** που διοργανώνουν events — δηλαδή τον χώρο/μαγαζί που σήμερα, όταν κάποιος πάει σε live, βρίσκει τα εισιτήρια μέσω link προς more.gr, ticketmaster.gr, ή αντίστοιχα, αντί μέσα από δικό του, ενοποιημένο σύστημα.

## Το πρόβλημα που εντοπίστηκε (πηγή έμπνευσης)

Παράδειγμα πραγματικό: ένα live stage στη Λάρισα διοργανώνει events, αλλά τα εισιτήρια πωλούνται μέσω εξωτερικών πλατφορμών (link από Instagram → more.gr/ticketmaster.gr). Καμία ενοποιημένη, δική τους εμπειρία.

## Ορολογία βιομηχανίας live events (ερευνήθηκε, τεκμηριωμένο)

Το σενάριο που περιέγραψε ο χρήστης αντιστοιχεί σε γνωστά, καθιερωμένα "deal structures" ανάμεσα σε artist/promoter/venue:

- **Flat guarantee**: Ο artist παίρνει σταθερή αμοιβή (π.χ. 2.000€), ανεξάρτητα από πωλήσεις εισιτηρίων. Ο promoter/venue αναλαμβάνει όλο το ρίσκο και κρατάει τα υπόλοιπα έσοδα (ή τη ζημιά).
- **Door split / percentage deal**: Ο artist παίρνει ποσοστό επί των εσόδων εισιτηρίων (π.χ. 70/30), αντί για σταθερό ποσό.
- **Guarantee vs. percentage ("versus deal")**: Ο artist παίρνει το μεγαλύτερο από τα δύο — είτε την εγγυημένη αμοιβή, είτε ποσοστό επί των εσόδων, ό,τι είναι μεγαλύτερο.
- **Promoter/manager model**: Ένας manager/booking agent πληρώνει *και* τον artist *και* το venue (αναλαμβάνει το ρίσκο), και τα έσοδα από τα εισιτήρια πάνε σε αυτόν.
- Ο χειροκίνητος διακανονισμός ανάμεσα στις πλευρές μετά το event ονομάζεται **"show settlement"** — υπάρχουν ήδη καθιερωμένες πρακτικές/έγγραφα γι' αυτό στη βιομηχανία, ανεξάρτητα από τεχνολογία.

## Αρχιτεκτονική ερώτηση (τεχνική, θα κριθεί στο κύριο technical brief)

Δύο εντελώς διαφορετικές προσεγγίσεις, με πολύ διαφορετικό κόστος υλοποίησης — αναλύθηκαν στη συζήτηση:

### Επιλογή Α — Απλή (ήδη συμβατή με το υπάρχον σύστημα, καμία επιπλέον δουλειά)
Κάθε event ανήκει σε **έναν** tenant μέσα στο Concerto (ήδη έτσι είναι το schema: `events.tenant_id`). Τα έσοδα από τα tickets πάνε σε **έναν** λογαριασμό. Ο διακανονισμός artist/venue/manager γίνεται **εκτός πλατφόρμας** (τραπεζικό έμβασμα, συμβόλαιο), όπως ήδη γίνεται σήμερα στη βιομηχανία. Το Concerto απλά πουλάει εισιτήρια για λογαριασμό ενός tenant.

### Επιλογή Β — Πραγματικό multi-party marketplace (μεγάλο, μελλοντικό feature)
Το Concerto **αυτόματα** μοιράζει τα έσοδα ενός ticket ανάμεσα σε πολλαπλές πλευρές (π.χ. 70% venue / 30% artist, ή flat fee + υπόλοιπο), μέσω πραγματικού split-payment συστήματος (π.χ. Stripe Connect). Απαιτεί: νέο data model (event stakeholders + κανόνες split), payment processor με υποστήριξη splits, "connected accounts" ανά tenant/venue. **Σημαντικό, ξεχωριστό feature, όχι κάτι για το τρέχον MVP/demo.**

**Σύσταση (δόθηκε στη συζήτηση):** Για τη συνάντηση/παρουσίαση τέλους μήνα, να προσεγγιστεί με βάση την Επιλογή Α (απλή, ήδη έτοιμη) — να ΜΗΝ δεσμευτεί ο χρήστης σε αυτόματο revenue-split ως "έτοιμο" feature πριν χτιστεί, καθώς θα έθετε σε κίνδυνο το ήδη στριμωγμένο χρονοδιάγραμμα του demo. Η Επιλογή Β παραμένει βιώσιμη, ελκυστική μελλοντική κατεύθυνση (πιθανή διαφοροποίηση από ανταγωνιστές όπως more.com/ticketmaster, που δεν καλύπτουν μικρά venues με αυτό τον τρόπο).

## Προτεινόμενες λύσεις από τον χρήστη (προς αξιολόγηση για τη συνάντηση)

### Λύση 1 — Venue αποκτά δικό του email/πρόσβαση για καταχώρηση events
Ιδέα: οι μπάντες λένε στον κάθε μαγαζάτορα "έχουμε δικό μας ticket service· δώσε μας ένα email, θα σου δώσουμε πρόσβαση να καταχωρείς εσύ το event και να βάζεις τον δικό σου λογαριασμό πληρωμής για τα εισιτήρια".

**Δύο ερμηνείες, διαφορετική δυσκολία:**
- **Ερμηνεία Α (απλή, ήδη αρχιτεκτονικά εφικτή, καμία νέα δουλειά):** Το venue γίνεται **δικός του tenant** μέσα στο Concerto — δική του σελίδα, δικά του events, τα εισιτήρια πωλούνται στον δικό του λογαριασμό. Οι μπάντες απλά αναφέρονται/συνδέονται. Ταυτίζεται πλήρως με το ήδη υπάρχον μοντέλο "1 event = 1 tenant owner" — απλά χρησιμοποιεί το ήδη σχεδιασμένο, μη χτισμένο **Tenant Admin Dashboard** (βλ. `concerto-admin-dashboard-brief.md`).
- **Ερμηνεία Β (πιο περίπλοκη):** Το venue καταχωρεί το event **μέσα στη σελίδα της μπάντας**, αλλά τα έσοδα πάνε σε ξεχωριστό λογαριασμό του venue. Αυτό είναι ουσιαστικά "ανάθεση πληρωμής ανά event" — ξαναμπαίνει στο πεδίο της **Επιλογής Β** (multi-party split) παραπάνω, όχι απλό.

**⚠️ Εκκρεμεί:** Ο χρήστης να διευκρινίσει ποια ερμηνεία εννοεί. Σύσταση: προχώρα με την Ερμηνεία Α για το άμεσο μέλλον/demo.

### Λύση 2 — Managers με δικό τους admin panel, πολλαπλών tenants
Ιδέα: ένας manager, αφού επιβεβαιωθεί (χειροκίνητα, από τον χρήστη προσωπικά, σε αυτό το στάδιο) ότι πράγματι εκπροσωπεί συγκεκριμένους tenants (π.χ. Tenant 1, Tenant 200, Tenant 35), αποκτά δικαίωμα να διαχειρίζεται/ανεβάζει events για **πολλαπλούς** tenants ταυτόχρονα.

**✅ Αξιολόγηση: απευθείας απαντά σε ήδη ανοιχτή ερώτηση του Tenant Admin Dashboard brief** ("μπορεί ένας admin να διαχειρίζεται πάνω από 1 tenant;") — η απάντηση είναι **ναι**, με many-to-many σχέση:
```sql
create table tenant_admins (
  id uuid primary key default gen_random_uuid(),
  user_id uuid references auth.users(id),
  tenant_id uuid references tenants(id),
  role text default 'admin',
  created_at timestamptz default now(),
  unique(user_id, tenant_id)
);
```
Πλήρως εφικτό, καμία επιπλέον πολυπλοκότητα πέρα από το ήδη σχεδιασμένο Dashboard. Η επιβεβαίωση ταυτότητας του manager γίνεται χειροκίνητα προς το παρόν (ο χρήστης προσωπικά, μέχρι να χρειαστεί πιο αυτοματοποιημένο invite-σύστημα στο μέλλον).

**Συμπέρασμα:** Και οι δύο λύσεις (στην απλή τους μορφή) εξαρτώνται από το **ίδιο, ήδη προγραμματισμένο αλλά μη χτισμένο** Tenant Admin Dashboard — δεν χρειάζονται νέα, ξεχωριστή αρχιτεκτονική. Αυτό ενισχύει την προτεραιότητα του Dashboard ως επόμενο μεγάλο technical task μετά το routing/checkout.

## ✅ ΤΕΛΙΚΗ ΑΠΟΦΑΣΗ: Cross-listing events με έγκριση (λύνει Λύση 1 + Λύση 2 μαζί, χωρίς split payments)

Μετά από συζήτηση, καταλήξαμε σε μεσαία λύση που συνδυάζει τα καλύτερα και των δύο προτάσεων, **χωρίς** να χρειαστεί ποτέ το δύσκολο Επιλογή Β (split payments/Stripe Connect).

### Η ιδέα
- Το venue (π.χ. "Live Stage Λάρισα") γίνεται **δικός του tenant** — ίδια σελίδα δομή με κάθε άλλο tenant, ενδεχομένως με λιγότερα tabs (θα οριστικοποιηθεί στην πορεία).
- Ο επιχειρηματίας (μέσω Tenant Admin Dashboard) δημιουργεί ένα event, με **δικό του** λογαριασμό πληρωμής — αυτός παραμένει ο **μοναδικός** ιδιοκτήτης των εσόδων του event, πάντα.
- Ταυτόχρονα, μπορεί να "tag-άρει" το event ώστε να ζητήσει να εμφανιστεί **ΚΑΙ** στη σελίδα ενός artist tenant (π.χ. των Villagers) — απλή **προβολή/cross-listing**, όχι μεταφορά χρημάτων.
- Το event εμφανίζεται στη σελίδα της μπάντας **μόνο μετά από έγκριση** — η μπάντα βλέπει "εκκρεμεί" στο δικό της Dashboard, πατάει OK, και μόνο τότε γίνεται ορατό δημόσια εκεί, με **όλες** τις λειτουργίες (ticket purchase κ.λπ.) — αλλά τα λεφτά συνεχίζουν να πάνε στον επιχειρηματία.
- **Η ίδια ακριβώς λογική δουλεύει και ανάποδα**: μια μπάντα φτιάχνει το δικό της event, το προτείνει προς εμφάνιση σε σελίδα ενός venue, ο επιχειρηματίας εγκρίνει.
- Managers (μέσω του ήδη αποφασισμένου many-to-many `tenant_admins`) χρησιμοποιούν τον ίδιο μηχανισμό, απλά διαχειρίζονται πολλαπλά tenants ταυτόχρονα.
- Σκοπός του approval step: αποφυγή scam/κατάχρησης (κάποιος να "κολλήσει" ψεύτικο event σε ξένη σελίδα χωρίς άδεια).

### Γιατί δουλεύει αρχιτεκτονικά, χωρίς νέο σοβαρό ρίσκο
Όταν κάποιος αγοράζει ticket, το σύστημα κοιτάει **ποιανού** είναι το event (πάντα `events.tenant_id`, αμετάβλητο) και στέλνει εκεί τα χρήματα — ανεξάρτητα από **ποια σελίδα** το έβλεπε ο fan όταν αγόρασε. Παραμένει **ένας ιδιοκτήτης πληρωμής ανά event**, όπως ήδη έχουμε σχεδιάσει — καμία ανάγκη για Stripe Connect ή split payments.

### Τεχνικό σχήμα (νέο table, θα υλοποιηθεί μαζί με το Tenant Admin Dashboard)
```sql
create table event_listings (
  id uuid primary key default gen_random_uuid(),
  event_id uuid not null references events(id) on delete cascade,
  listed_tenant_id uuid not null references tenants(id) on delete cascade,
  status text not null default 'pending' check (status in ('pending', 'approved', 'rejected')),
  requested_by uuid references auth.users(id),
  created_at timestamptz default now(),
  approved_at timestamptz,
  unique (event_id, listed_tenant_id)
);
```
`events.tenant_id` παραμένει πάντα ο ιδιοκτήτης-πληρωμής. Το `event_listings` είναι απλά "αιτήματα προβολής" σε άλλες σελίδες, με έγκριση.

**Δεν έχει οριστεί ακόμα:** αυστηρό χρονικό όριο (π.χ. 24ωρο) για την έγκριση — αναφέρθηκε "μία μέρα" χαλαρά, όχι ως σκληρό technical requirement. Να διευκρινιστεί αν χρειάζεται πραγματικό deadline/expiry αργότερα.

**Εξάρτηση:** Αυτό το feature **χτίζεται μαζί με** το Tenant Admin Dashboard (δεν μπορεί να γίνει ξεχωριστά, αφού χρειάζεται UI για create/approve/reject σε επίπεδο tenant admin). Ενημερώθηκε αντίστοιχα το `concerto-admin-dashboard-brief.md`.

## 🔑 ΜΕΓΑΛΗ ΣΥΖΗΤΗΣΗ: Custom Domains vs Subdomains + Global SSO (τεκμηριωμένη, με πραγματική έρευνα)

Προέκυψε ερώτημα: αν κάθε tenant αποκτήσει πραγματικό δικό του domain (π.χ. `villagers.gr` αντί για `villagers.concerto.gr`), τι σημαίνει αυτό για το μελλοντικό ενιαίο "Concerto Family" login/εμπειρία;

### Το βασικό μοντέλο fan/tenant — επιβεβαιώθηκε σωστό, καμία αλλαγή
Ο fan είναι ήδη **global** στη βάση (`fans` table), ανεξάρτητα από ποιο tenant site επισκέφτηκε πρώτα. Κάθε tenant βλέπει μόνο τους δικούς του fans μέσω RLS, μέχρι να τον ακολουθήσουν. Αυτό παραμένει σωστό ό,τι κι αν αποφασιστεί για domains.

### Το πρόβλημα: "αυτόματο login παντού" με custom domains

**Ιδέα που εξετάστηκε (και απορρίφθηκε ως αναξιόπιστη):** "Silent SSO" — όταν ο fan επισκέπτεται ένα νέο tenant domain, το site "ρωτάει αθόρυβα" (μέσω κρυφού iframe) ένα κεντρικό domain "τον ξέρεις;". **Τεκμηριωμένο εύρημα (έρευνα 2026):** Αυτή η τεχνική είναι ήδη αναξιόπιστη σε μεγάλο μέρος του web — Safari και Firefox μπλοκάρουν εξ ορισμού cross-site cookie/iframe επικοινωνία (privacy protection), και το Chrome το έχει κάνει opt-in (οι περισσότεροι χρήστες δεν συναινούν). Θα δούλευε σπασμένα για σημαντικό μέρος του κοινού — **δεν προτείνεται**.

**Η σωστή, σύγχρονη λύση: Redirect-based bridge (σαν δικό μας "Sign in with Google")**
Αντί για κρυφό κόλπο, πλήρης ανακατεύθυνση: fan πατάει "Σύνδεση" στο `villagers.gr` → μεταφέρεται πραγματικά (πλήρες page navigation, όχι iframe) στο `concertofamily.gr` → εκεί συνδέεται/αναγνωρίζεται → επιστρέφει στο `villagers.gr` με "εισιτήριο" (session token). Ακριβώς ο ίδιος μηχανισμός με το ήδη υπάρχον Google OAuth redirect flow — δεν εξαρτάται από cookies που μπλοκάρονται.

**⚠️ Διευκρίνιση ασφαλείας (σημαντική, να μην ξεχαστεί):** Αυτό **ΔΕΝ** σημαίνει ότι το Concerto αποθηκεύει κωδικούς χρηστών. Ο Google παραμένει ο μόνος που επαληθεύει το πραγματικό password — το μόνο που αλλάζει είναι **πού** γίνεται η κλήση προς τον Google (μέσω ενός κεντρικού `concertofamily.gr` bridge αντί απευθείας από κάθε tenant site). Αποθηκεύουμε **μόνο** session token, όπως ήδη κάνουμε σήμερα — καμία νέα, ευαίσθητη πληροφορία.

**Ρεαλιστική εκτίμηση κόστους/χρόνου:** Αυτό είναι **μεγαλύτερο** από το ήδη περίπλοκο single-domain login που χτίσαμε (4 bugs, ολόκληρη συνεδρία). Χρειάζεται: δική του mini-εφαρμογή (`concertofamily.gr`), ασφαλής μηχανισμός ανταλλαγής token (προστασία από κλοπή/replay), λίστα επιτρεπόμενων redirect domains (αλλιώς κίνδυνος "open redirect" ασφαλείας), δοκιμές σε πολλαπλά πραγματικά domains. **Εκτίμηση: τουλάχιστον 2-3 ολόκληρες αφιερωμένες συνεδρίες.** ΔΕΝ γίνεται παράλληλα με το routing του Σαββάτου.

**✅ ΑΠΟΦΑΣΗ: ΟΧΙ πριν το demo/launch.** Κανένας tenant δεν έχει σήμερα πραγματική ανάγκη custom domain — παραμένουμε στο subdomain μοντέλο (`*.concerto.gr`) για τώρα. Το custom-domain + SSO bridge παραμένει βιώσιμη, ελκυστική μελλοντική κατεύθυνση, να επανεξεταστεί μετά το πρώτο launch, με άνετο χρόνο.

### Subdomain μοντέλο (`*.concerto.gr`) — πλεονεκτήματα/μειονεκτήματα

**Πλεονεκτήματα:**
- Αυτόματο SSO μέσα στην οικογένεια, ΔΩΡΕΑΝ — μία απλή ρύθμιση cookie (`Domain=.concerto.gr`), καμία ανάγκη για bridge system
- Brand recognition — κάθε site δείχνει ότι ανήκει σε αναγνωρίσιμο δίκτυο (θετικό και για sales story: "μπαίνεις σε growing network")
- Απλούστερη υποδομή γενικά (ένα wildcard SSL πιστοποιητικό μπορεί να καλύψει όλα τα subdomains)

**Μειονεκτήματα:**
- Λιγότερο "δικό μου, ανεξάρτητο site" αίσθημα για μεγαλύτερες μπάντες που θέλουν πλήρη brand ανεξαρτησία
- Μελλοντικό κόστος αν χρειαστεί custom domain (το SSO bridge παραπάνω)

### 🔬 Τεκμηριωμένα ευρήματα για scaling σε 20K fans + 30 tenants

**1. Google OAuth ΔΕΝ υποστηρίζει wildcard origins (επιβεβαιωμένο, επίσημη τεκμηρίωση Google):** *"Authorized JavaScript origins field doesn't allow wildcards."* Αυτό σημαίνει ότι **ανεξάρτητα** από subdomain ή custom domain στρατηγική, **κάθε νέο tenant site** (π.χ. το 30ό venue) θα χρειάζεται να προστεθεί **χειροκίνητα** στη λίστα Google Cloud Console. Δεν είναι κάτι που "σπάει"/κρασάρει — είναι επαναλαμβανόμενο, χειροκίνητο βήμα ανά onboarding. **⚠️ TODO μελλοντικό:** να μπει ως ρητό βήμα στο checklist onboarding νέου tenant μέσα στο μελλοντικό Tenant Admin Dashboard, ώστε να μη ξεχνιέται.

**2. Ασφάλεια δεδομένων ανεξάρτητη από domain στρατηγική:** Το ποιος βλέπει/επεξεργάζεται τι δεδομένα καθορίζεται αποκλειστικά από τα ήδη υπάρχοντα RLS policies στη βάση — όχι από το αν χρησιμοποιούμε subdomains ή custom domains. Το ίδιο μοντέλο ασφάλειας δουλεύει ίδια σε 2 ή 300 tenants, καμία αλλαγή χρειάζεται.

**3. "Δεν κρασάρει" η βάση σε 20K fans:** Ήδη ερευνημένο παλιότερα (βλ. ενότητα SCALABILITY) — μικρός αριθμός για PostgreSQL/Supabase, με production παραδείγματα 50K+ χρηστών. Το μόνο πραγματικό εκκρεμές παραμένει το **database indexing** (ήδη σημειωμένο, ανεξάρτητο ζήτημα από domain στρατηγική).

**4. ⚠️ Πραγματική υποδομή wildcard — ΔΕΝ έχει δοκιμαστεί ακόμα στην πράξη.** Μέχρι στιγμής έχουμε δοκιμάσει μόνο: (α) τοπικά μέσω `/etc/hosts`, (β) ένα μεμονωμένο Netlify URL χειροκίνητα συνδεδεμένο σε έναν tenant (`concertofamily.netlify.app`). Το πραγματικό wildcard σύστημα production (αγορά `concerto.gr`, DNS ρύθμιση `*.concerto.gr` → Netlify, επιβεβαίωση ότι το Netlify δέχεται σωστά wildcard custom domains σε επίπεδο DNS/SSL) είναι πραγματικό, ανοιχτό task για πριν το launch — δεν έχει επιβεβαιωθεί ότι δουλεύει ήδη σε πολλαπλά (πόσο μάλλον 30) domains.
